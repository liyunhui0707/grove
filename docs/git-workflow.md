## 每项工作的开始与结束

```sh
git status --short --branch
git log -5 --oneline
git branch -vv
```

1. 先识别已有改动、当前分支和上游；保护无关工作，不用 reset/clean/强制 checkout 清场。需要续接同阶段就沿用其分支；新阶段从正确基线建分支，不机械丢弃尚未整合的改进。
2. 按一个可评审行为拆提交，代码、相关回归和必要说明一起提交。Git 小提交不等于让用户逐步签核。阶段文档保持精简，原始日志和个人路径放忽略区。
3. 运行与风险相称的检查。区分本轮运行、复用既有证据、未验收范围。原生测试绑定 build ID 与源清单；浏览器模拟不冒充原生通过。
4. 明确列出文件再 `git add -- <files>`；检查 `git diff --cached --stat` 和 `git diff --cached`，确认无运行数据、个人路径、凭据、调试文件或无关改动，再执行 `git diff --cached --check`。
5. 用具体提交说明记录行为、验证和限制。所有者已授权日常阶段本地提交，无须逐次请求；阶段完成时产品改动应已提交，剩余 WIP 须明确解释。状态文档不能代替 Git 提交。
6. 报告分支、提交、工作区状态及是否已推送。仅本地完成不说成 GitHub 已同步。

## 远端、版本与候选

读取和同步引用时核对远端 main、标签及实际提交对象；禁止强制重写已发布历史或移动版本标签。网络 fetch 不通时可用只读 API 核对引用，但必须验证本地对象存在，并明确记录实际同步方法。

本地提交不等于推送/PR/发版授权。推送、GitHub 写操作、标签、版本递增、安装包发布和官网部署遵循当前任务的明确授权；不要自动扩大范围。发布前将受验源码提交与 build ID、源文件清单、产物散列对应，区分构建、安装、原生验收、已发布四种状态。历史已接受二进制不因补记 Git 提交而改 build ID 或声称重新构建。

`.local/`、媒体、SQLite/WAL、缓存、导出、日志、签名材料和私人历史始终忽略，绝不 force-add。凭据审查只检查名称和机制，不读取受保护值。

## 官网

官网源码在 `website/`，在产品仓库中必须是普通文件（mode 100644/100755），不能是 mode 160000 的 gitlink。Sites 所需本地元数据保持原状。只有网站实际变更时，才同步其工具历史及部署版本；不可只提交父仓库就声称已部署。
